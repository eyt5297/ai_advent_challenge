# ТЗ: агенты как отдельная сущность

Переделка бэкенда. Документ описывает целевое состояние, а не процесс.
Действующее ТЗ каркаса — `SPEC.md`; здесь только то, что меняется.

---

## 1. Зачем

Сейчас домен состоит из сессий и сообщений. Сессия — это папка с перепиской,
а настройки модели живут прямо в ней. Такая модель описывает чат, но не
описывает агента: нет сущности, которую можно настроить один раз и запускать
многократно.

Целевая модель:

> **Агент** — настроенный исполнитель. **Сессия** — его запущенный экземпляр.
> **Чат** — окно наблюдения: выдать задание, получить ответ, видеть обмен
> между агентом и LLM.

Главное следствие: обмен с LLM перестаёт быть единицей взаимодействия и
становится *шагом*. Пользователь выдаёт задание, агент делает N обращений к
модели, пользователь получает результат и может развернуть шаги.

---

## 2. Модель предметной области

```
Agent          настройка: имя, промпт, модель, параметры, лимиты
  │            живёт независимо от запусков, переиспользуется
  ↓ 1:N
Session        экземпляр агента: «запуск №3 агента Рецензент»
  │            наследует настройки, может переопределить
  ↓ 1:N
Task           задание: ваш текст + итог + статус
  │            единица наблюдения, то, что видно в ленте свёрнутым
  ↓ 1:N
Message        шаг: один обмен с LLM (пара запрос/ответ, как сейчас)
```

### 2.1 Где лежит статус

**Статус принадлежит заданию, а не сессии.** Это снимает вопрос «агент —
долгоживущий диалог или одноразовая задача»: он и то, и другое.

- Сессия живёт долго и накапливает задания — как сейчас живёт чат.
- Задание имеет жизненный цикл `running` → `done` | `failed` | `cancelled`.

Так левая панель остаётся простой, а индикатор работы появляется ровно там,
где идёт работа. Если бы статус был у сессии, пришлось бы решать, что
означает «завершённая сессия, в которую пришло новое задание».

### 2.2 Что наследуется

| Поле | Агент | Сессия | Приоритет |
|---|---|---|---|
| `system_prompt` | обязательно | — | агента |
| `provider_id` / `model_id` | обязательно | переопределение | сессии, если задано |
| `params` (temperature и пр.) | значения по умолчанию | переопределение | по полю: сессия поверх агента |
| `max_steps` | обязательно | — | агента |
| `tools` (п. 11.3) | обязательно | — | агента |

Переопределение на уровне сессии нужно для сравнения: запустить того же
агента на другой модели и сопоставить поведение. Это дешёвая возможность,
потому что поля в `sessions` уже есть — меняется только их трактовка
(было «настройка», стало «переопределение, `NULL` = как у агента»).

## 3. Схема БД

Миграции **только добавляются в конец** списка `migrations()` в
`server/src/server/db.gleam`. Существующие версии не трогаются.

> Реализовано как миграция **3**: номер 2 занял этап 0 (уникальный индекс
> по `seq` и `reply_to`). Нумерация ниже приведена к фактической.

```sql
-- 3: агенты, задания и привязка сообщений к шагам

CREATE TABLE agents (
  id           TEXT PRIMARY KEY,
  name         TEXT NOT NULL,
  description  TEXT NOT NULL DEFAULT '',
  system_prompt TEXT NOT NULL DEFAULT '',
  provider_id  TEXT NOT NULL,
  model_id     TEXT NOT NULL,
  params_json  TEXT,
  max_steps    INTEGER NOT NULL DEFAULT 1,
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL
);

CREATE TABLE tasks (
  id         TEXT PRIMARY KEY,
  session_id TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  seq        INTEGER NOT NULL,
  prompt     TEXT NOT NULL,     -- задание пользователя
  result     TEXT,              -- итог, NULL пока не готов
  status     TEXT NOT NULL,     -- running | done | failed | cancelled
  error      TEXT,
  steps      INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL,
  finished_at INTEGER
);

ALTER TABLE sessions ADD COLUMN agent_id TEXT REFERENCES agents(id);
ALTER TABLE messages ADD COLUMN task_id  TEXT REFERENCES tasks(id) ON DELETE CASCADE;
ALTER TABLE messages ADD COLUMN step     INTEGER;

-- Номер задания присваивается внутри INSERT, как у сообщений (п. 8.3);
-- индекс страхует от повторения при параллельном создании.
CREATE UNIQUE INDEX idx_tasks_seq ON tasks(session_id, seq);
CREATE INDEX idx_tasks_session ON tasks(session_id, seq);
CREATE INDEX idx_messages_task ON messages(task_id, step);
CREATE INDEX idx_sessions_agent ON sessions(agent_id);
```

В таблице `agents` есть и `tools_json` — поле заполнится на этапе 3,
но добавлено сразу: отдельная миграция ради одной колонки не нужна.

### 3.1 Старые данные

В `data/chat.db` лежат реальные сессии ручного тестирования. Миграция не
должна их ломать.

- `sessions.agent_id` у старых строк остаётся `NULL` — это **сессия без
  агента**, поведение прежнее: сообщение → запрос → ответ.
- `messages.task_id` у старых строк остаётся `NULL` — такие сообщения
  показываются в ленте плоско, как сейчас.

Служебный агент «по умолчанию» не создаётся. Соблазн есть, но он превращает
`NULL` в скрытое состояние и усложняет чтение кода: лучше честный
`Option(Agent)`, который компилятор заставит разобрать.

### 3.2 Чего не делаем

`ALTER TABLE ... ADD COLUMN` в SQLite не умеет добавлять `NOT NULL` без
значения по умолчанию, и не умеет добавлять внешний ключ с проверкой задним
числом. Обе колонки сделаны `NULL`-овыми намеренно — пересоздавать таблицы
ради строгости не нужно, целостность обеспечивает код репозитория.

### 4.2 Совместимость с клиентом

Ранее обсуждался строгий вариант: заморозить `shared` и конвертировать на
границе. От него отказываемся — здесь он не окупается.

Причина: контрактный тест проверяет наличие полей, а не их полноту
(`hasKeys` допускает лишние ключи). Значит **добавление** полей контракт не
ломает. Все правки выше — именно добавления, ни одно поле не удаляется и не
меняет тип. Клиент продолжит работать, не зная об агентах.

Правило на время переделки: **в `shared` разрешено только добавлять**.
Удаление или смена типа поля требует отдельного решения и правки клиента.

## 5. HTTP API

### 5.1 Новые эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/agents` | Список агентов (`AgentSummary`) |
| `POST` | `/api/agents` | Создать агента |
| `GET` | `/api/agents/:id` | Агент целиком |
| `PATCH` | `/api/agents/:id` | Частичное обновление, как у сессий |
| `DELETE` | `/api/agents/:id` | Удалить. Запрещено, если есть сессии → `409` |
| `POST` | `/api/agents/:id/sessions` | Запустить экземпляр: создать сессию агента |
| `GET` | `/api/sessions/:id/tasks` | Задания сессии со статусами |
| `POST` | `/api/sessions/:id/tasks` | Выдать задание. Запускает цикл агента |
| `GET` | `/api/tasks/:id` | Задание + его сообщения (шаги) |
| `DELETE` | `/api/tasks/:id` | Удалить задание со всеми шагами |

`DELETE /api/agents/:id` отвечает `409` с кодом `agent_in_use`, а не удаляет
каскадом. Каскад здесь опасен: за агентом стоит история запусков, и потерять
её по одному клику — неприемлемо. Удаление сессий — отдельное осознанное
действие.

**Проверки при сохранении агента** (а не при запуске — иначе агент
создавался бы успешно и ломался потом, когда связь с ошибкой уже не
очевидна):

| Код | Когда |
|---|---|
| `empty_name` | имя из одних пробелов |
| `unknown_provider` | провайдера нет в каталоге |
| `unknown_model` | модели нет у этого провайдера |
| `invalid_max_steps` | вне диапазона 1…50 |

Диапазон `max_steps` ограничен сверху намеренно: это защита от
зацикливания, и значение в тысячу шагов почти наверняка опечатка.

### 5.2 Что сохраняется без изменений

Все 10 существующих эндпоинтов работают как прежде, включая `preview` и
`send`. Они остаются рабочим режимом для сессий без агента и инструментом
отладки: отправить один запрос вручную, минуя цикл агента, — именно то, ради
чего каркас строился.

Контрактный тест `e2e/api_contract_test.mjs` должен остаться зелёным
**без правок**. Это приёмочный критерий переделки.

### 5.3 Формы запросов и ответов

```jsonc
// POST /api/agents
{
  "name": "Рецензент",
  "description": "Разбирает текст по критериям",
  "system_prompt": "Ты строгий редактор…",
  "provider_id": "veai",
  "model_id": "Anthropic/sonnet-5",
  "params": { "temperature": 0.3 },
  "max_steps": 5
}
// → 201, объект Agent

// POST /api/sessions/:id/tasks
{ "prompt": "Проверь этот абзац: …" }
// → 200
{
  "task": { "id": "tsk_…", "status": "done", "result": "…", "steps": 3 },
  "messages": [ /* Message, по 2 на каждый шаг */ ],
  "warnings": []
}
```

Ответ `POST /tasks` отдаёт задание **целиком, по завершении** — блокирующе,
как сейчас `send`. Есть и асинхронный режим `?async=true`, возвращающий
`202` сразу (п. 10.3). Стриминг вынесен в этап 4 (п. 12).

### 5.4 Ошибки

Формат прежний: `{"error": {"code": …, "message": …}}`. Новые коды:

| Код | Статус | Когда |
|---|---|---|
| `agent_not_found` | 404 | Неизвестный `agent_id` |
| `agent_in_use` | 409 | Удаление агента с сессиями |
| `task_not_found` | 404 | Неизвестный `task_id` |
| `session_without_agent` | 400 | Задание в сессию без агента |
| `step_limit_reached` | — | Не ошибка HTTP: задание получает `status = failed` |

Последнее важно: исчерпание лимита шагов — это результат работы агента, а не
сбой сервера. Оно сохраняется в задании вместе со всеми шагами, чтобы было
видно, на чём агент зациклился. Тот же принцип, по которому сейчас ошибка
провайдера становится сообщением, а не HTTP-ошибкой.

## 6. Три точки расширения

Форма всех трёх сохраняется. Это проверка качества каркаса: если агенты
потребуют смены сигнатур, значит границы были проведены неверно.

### ★1 `build_request_body` — `server/src/server/llm/request.gleam`

Меняется **содержимое `RequestContext`**, а не функция.

```gleam
pub type RequestContext {
  RequestContext(
    …существующие поля…,
    /// История шагов внутри текущего задания.
    /// Пусто для первого шага и для сессий без агента.
    history: List(Message),
  )
}
```

Внутри функции появляется сборка `messages` из истории вместо одного
элемента. `system_prompt` по-прежнему берётся из `options` — его туда кладёт
слой слияния настроек (п. 7.1), поэтому `build_request_body` не знает об
агентах вовсе.

Это ключевое решение всего ТЗ: **точка расширения не должна знать про
агентов**. Она собирает тело запроса из того, что ей дали.

### ★2 `parse_response_body` — `server/src/server/llm/response.gleam`

Не меняется совсем. Ответ модели разбирается одинаково независимо от того,
кто его запросил.

### ★3 `send` — `server/src/server/llm/client.gleam`

**Не меняется ни на одном этапе, включая четвёртый.**

Изначально предполагалось, что стриминг потребует здесь второй функции
`send_streaming`. Не потребовал: этап 4 передаёт по SSE готовые шаги, а не
токены (п. 14.2), поэтому транспорт до провайдера остался нетронутым.

Это главный итог проверки каркаса: все три точки расширения пережили
переделку домена без смены сигнатур.

## 7. Цикл агента

Новый модуль `server/src/server/agent/loop.gleam`. Оркестрация, как
`llm/chat.gleam`, но над заданиями.

```
run_task(agent, session, prompt):
  создать Task(status: running)
  история = []
  шаг = 1
  цикл:
    если шаг > agent.max_steps:
      Task(status: failed, error: "исчерпан лимит шагов")
      выход
    опции   = merge_options(agent, session)
    запрос  = chat.prepare(…, history, опции)
    пара    = chat.send(запрос)          ← существующий код целиком
    сохранить пару с task_id и step = шаг
    если пара.assistant.status == error:
      Task(status: failed, error: …)
      выход
    если завершено(пара.assistant):
      Task(status: done, result: пара.assistant.content, steps: шаг)
      выход
    история = история + пара
    шаг = шаг + 1
```

`chat.send` переиспользуется целиком — цикл агента надстраивается над ним,
а не заменяет его. Сохранение сообщений, сырых тел, латентности и токенов
продолжает работать без правок.

### 7.0 Атрибуция шагов

`chat.send` получил параметр `Attribution`:

```gleam
pub type Attribution {
  /// Ручная отправка в сессии без агента.
  Standalone
  /// Шаг внутри задания.
  Step(task_id: String, step: Int)
}
```

Отдельный тип вместо пары необязательных аргументов: так нельзя задать
номер шага без задания или наоборот — компилятор не даст.

Побочный эффект, который пришлось учесть: автозаголовок сессии
(`sessions.autotitle`) при шаге агента **не срабатывает**. Запуск уже
назван по агенту, и подменять это текстом служебного шага было бы
неожиданно.

### 7.1 Слияние настроек

Отдельная функция, которая и есть вся «агентность» в слое запроса:

```gleam
/// Настройки агента, поверх них — переопределения сессии.
/// Выделено отдельно, чтобы точки расширения не знали про агентов.
pub fn merge_options(agent: Agent, session: Session) -> RequestOptions
```

Правило: непустое поле сессии побеждает, `None` означает «как у агента».
`system_prompt` берётся у агента всегда — это его определяющее свойство,
переопределять его на уровне запуска значит запускать другого агента.

### 7.2 Признак завершения

На этапах 1–3 `max_steps = 1` у всех агентов, и цикл делает ровно один
проход: задание = один обмен. Функция `завершено` возвращает `True` всегда.

Многошаговость включается этапом 3a вместе с инструментами, когда появится
честный критерий: модель вернула текст (`TextAnswer`) или просит вызвать
инструмент (`ToolCalls`) — см. п. 11.5. Выдумывать критерий раньше
(например, искать «ГОТОВО» в тексте) — плохая идея: такой признак ненадёжен
и потом мешает.

До этого момента таблица `tasks` и цикл уже работают, просто цикл всегда
однопроходный. Это позволяет развернуть структуру и UI, не дожидаясь
инструментов.

## 8. Параллельная работа

Агенты работают параллельно. Это следует из устройства BEAM: каждый
HTTP-запрос обслуживает отдельный процесс, а NIF-вызовы `esqlite` помечены
`ERL_NIF_DIRTY_JOB_IO_BOUND` — то есть уходят на грязные планировщики и не
блокируют остальные процессы.

### 8.1 Измерено на практике

Сервер с медленным моком (3 секунды на ответ), шесть одновременных запросов
в разные сессии:

```
ses_GkQ…  3.076 с
ses_M0j…  3.076 с
ses_2Q-…  3.076 с
ses_EcL…  3.076 с
ses_-OY…  3.076 с
ses_y1n…  3.077 с
общее: 3084 мс
```

Шесть запросов по три секунды уложились в три секунды — сериализации нет.
Все двенадцать строк записались в БД корректно.

Это даётся бесплатно тремя решениями, которые уже приняты в каркасе:

- **WAL** (`PRAGMA journal_mode = WAL`) — чтение не блокируется записью;
- **`busy_timeout = 5000`** — конкурирующая запись ждёт, а не падает;
- **`httpc` поверх процессов** — долгий запрос к LLM занимает только свой
  процесс.

### 8.2 Где параллельность ломается: гонка за `seq`

Проверка параллельных запросов **в одну сессию** нашла настоящий дефект.
Четыре одновременных `send`:

```
seq role       content
1   user       запрос 2
2   assistant  ок
2   user       запрос 1      ← дубль
2   user       запрос 4      ← дубль
3   assistant  ок
3   assistant  ок
3   user       запрос 3      ← дубль
4   assistant  ок
```

Причина в `messages.next_seq`:

```sql
SELECT COALESCE(MAX(seq), 0) + 1 FROM messages WHERE session_id = ?
```

Между `SELECT` и последующим `INSERT` проходит весь запрос к LLM — секунды.
За это время соседний процесс читает тот же максимум. Классический
read-modify-write без атомарности.

Сейчас это не проявляется: интерфейс блокирует кнопку отправки на время
запроса, поэтому второй запрос в ту же сессию физически не уходит. Но
**агенты снимают эту защиту** — цикл агента пишет сообщения сам, и два
задания в одной сессии дадут ровно такую картину.

### 8.3 Решение: присваивать `seq` внутри INSERT

Чтение максимума и вставка должны стать одним оператором:

```sql
INSERT INTO messages (id, session_id, seq, …)
SELECT ?, ?, COALESCE(MAX(seq), 0) + 1, …
  FROM messages WHERE session_id = ?
```

SQLite выполняет оператор атомарно, поэтому гонка исчезает. Публичная
функция `next_seq` при этом удаляется: сама её возможность вызвать отдельно
и есть источник дефекта. Оставлять её «на всякий случай» — значит оставить
грабли.

Дополнительно ставится ограничение, которое превращает молчаливую порчу
данных в честную ошибку:

```sql
CREATE UNIQUE INDEX idx_messages_seq ON messages(session_id, seq);
```

Индекс создаётся миграцией 2 вместе с остальным. Если в существующей базе
уже есть дубли — миграция упадёт, и это правильное поведение: лучше
отказаться стартовать, чем работать на испорченных данных.

> Проверено на копии `data/chat.db`: дублей нет, миграция прошла,
> 12 сообщений читаются.

### 8.3.1 Следствие: пара больше не соседствует по `seq`

Обнаружено при проверке исправления. Атомарная вставка решила гонку, но
номера пары перестали быть соседними: пока идёт запрос к провайдеру,
между ним и его ответом вклиниваются чужие строки.

```
seq  role       content       было ожидание: 1-2, 3-4, …
1    user       запрос 4
2    user       запрос 5      ← чужой запрос между парой
…
11   assistant  ок            ← ответ на «запрос 4»
```

`delete_exchange` искал пару по `seq ± 1` и после исправления стал
оставлять ответы сиротами. То есть это тот же дефект, просто другое его
проявление: **связь выводилась из данных вместо того, чтобы храниться.**

Решение — явное поле:

```sql
ALTER TABLE messages ADD COLUMN reply_to TEXT REFERENCES messages(id);
CREATE INDEX idx_messages_reply ON messages(reply_to);
```

Поиск пары идёт в обе стороны: потянули за запрос — уйдёт строка с
`reply_to = id`, потянули за ответ — уйдёт строка с `id = reply_to`.

Для сообщений, записанных до миграции, поле `NULL`, и для них сохраняется
прежний поиск по соседству. Условие в запросе устроено так, что запасной
путь срабатывает **только** при отсутствии связи у обеих строк — иначе он
мог бы захватить лишнее.

Поле добавлено и в `shared/types.Message` с декодером через
`optional_field`: сохранённые ранее тела ответов его не содержат.

### 8.4 Что ещё сериализуется и нужно ли это чинить

**Запись в SQLite.** У WAL один писатель одновременно. Транзакция записи
пары сообщений занимает миллисекунды против секунд работы LLM, поэтому
очередь на запись несущественна. Пул соединений не нужен.

**Параллельные задания одной сессии.** Технически возможны после правки
`seq`, но семантически сомнительны: агент с историей шагов получит
чересполосицу. Решение: **задания одной сессии выполняются последовательно**.
Если в сессии уже есть задание со `status = running`, новое получает
`409 task_already_running`.

Это ограничение на уровне сессии, а не агента: разные запуски одного агента
работают параллельно — именно для этого сессия и является экземпляром.

### 8.5 Что это даёт

| Сценарий | Параллельно |
|---|---|
| Разные агенты | да |
| Разные сессии одного агента | да |
| Задания в одной сессии | нет, по решению выше |
| Шаги внутри задания | нет, они последовательны по смыслу |

Отдельный пул процессов, акторы или очередь заданий не нужны. BEAM уже
предоставляет нужную модель, и городить поверх неё свою — лишняя работа.

### 8.6 Приёмочный тест

В `e2e/` добавляется `09_concurrency_test.mjs`: поднимает мок с задержкой,
пускает N параллельных заданий в разные сессии и проверяет, что

1. общее время ≈ время одного запроса, а не их сумма;
2. `seq` в каждой сессии строго возрастает без дублей;
3. параллельное задание в занятую сессию отвергается с `409`.

## 9. Интерфейс

Интерфейс пользователя устраивает — меняем по минимуму.

### 9.1 Левая панель

Становится двухуровневой:

```
▾ Рецензент              ← агент
    запуск 14:32  ✓
    запуск 12:10  ✓
▾ Переводчик
    запуск 09:41  ✗
  + Новый агент
```

Сессии без агента (старые) показываются отдельной группой «Без агента»
внизу. Механика выбора, удаления и переименования прежняя.

### 9.2 Лента

Двухуровневая: задание свёрнуто в карточку, шаги раскрываются.

```
┌ Задание                             ✓ 3 шага  2.4 с
│ Проверь этот абзац: …
├ ▸ Шаги (3)                         ← свёрнуто по умолчанию
└ Итог
  В абзаце две проблемы…
```

Внутри «Шагов» — существующий компонент сообщения без изменений, вместе с
кнопками `{} JSON` и удаления. Это и есть «наблюдение за обменом между
агентом и LLM»: ничего нового изобретать не нужно, достаточно вложить
имеющееся.

Для сессий без агента (`task_id = NULL`) лента остаётся плоской, как сейчас.

### 9.3 Панель настроек

Селекты провайдера и модели и панель `⚙` переезжают из `composer` в
**карточку агента** — новый экран, открывается по клику на имени агента.
В сессии остаётся та же панель с пометкой «переопределить для этого
запуска», свёрнутая по умолчанию.

Composer сокращается до поля ввода и кнопки «Выдать задание».

## 10. Задел под внешние каналы

Веб-интерфейс — не единственный возможный способ управлять агентами. Телеграм-
бот, расписание, вебхук — всё это со временем вероятно. Отдельный супервизор
под такие запуски писать **сейчас не нужно**, но три решения стоит принять
заранее: переделывать их потом дороже, чем заложить сразу.

Раздел ничего не добавляет к объёму этапов 0–3. Это ограничения, а не работа.

### 10.1 Ядро не зависит от HTTP

Правило: **модули `llm/` и `agent/` не импортируют `wisp` и `mist`.**

Сейчас это уже так. Ядро принимает соединение с БД и конфиг:

```gleam
pub fn send(
  connection: Connection,
  config: Config,
  session: Session,
  prepared: Prepared,
  content: String,
) -> Result(Exchange, ChatError)
```

Ни `wisp.Request`, ни заголовков, ни сессии HTTP. Цикл агента
(`agent/loop.gleam`) обязан иметь такую же форму:

```gleam
pub fn run_task(
  connection: Connection,
  config: Config,
  agent: Agent,
  session: Session,
  prompt: String,
) -> Result(Task, TaskError)
```

Благодаря этому `main` расширяется добавлением ветки, а не переделкой:

```
db.connect → Context ─┬→ mist.start          HTTP (сейчас)
                      ├→ telegram.start      бот (потом)
                      └→ scheduler.start     расписание (потом)
```

`Context` — обычная запись, её собирает кто угодно. Соединение с БД одно на
процесс ОС и делится между каналами: вызовы `esqlite` помечены
`ERL_NIF_DIRTY_JOB_IO_BOUND`, поэтому не блокируют друг друга (п. 8).

Проверка правила — одна строка в CI:

```bash
grep -rn "import wisp\|import mist" server/src/server/llm server/src/server/agent \
  && echo "ядро не должно знать про HTTP" && exit 1
```

### 10.2 Состояние задания — в БД, а не в памяти процесса

Уже заложено: `tasks.status`, `tasks.steps`, `tasks.result` (п. 3).

Соблазн держать состояние выполняющегося задания в процессе и отдавать его
через сообщения — есть, и для одного канала это было бы быстрее. Но тогда
бот не сможет узнать о ходе работы, не получив доступ к `Pid`, а после
перезапуска сервера состояние исчезнет вместе с процессом.

Правило: **процесс, выполняющий задание, не является источником правды.**
Он пишет в БД после каждого шага; любой канал читает оттуда же.

Цена — один `UPDATE` на шаг. На фоне секунд ожидания LLM это ничто.

### 10.3 Асинхронный режим эндпоинта — сразу

`POST /api/sessions/:id/tasks` получает необязательный параметр:

```jsonc
// синхронно (по умолчанию) — как описано в п. 5.3
POST /api/sessions/:id/tasks
{ "prompt": "…" }
// → 200, задание целиком по завершении

// асинхронно
POST /api/sessions/:id/tasks?async=true
{ "prompt": "…" }
// → 202
{ "task": { "id": "tsk_…", "status": "running", "steps": 0 } }
```

Ход работы читается через `GET /api/tasks/:id` — тот же эндпоинт, что и для
веба.

Почему сразу, хотя бот ещё не нужен: добавить параметр к эндпоинту потом
легко, а вот **переучить клиента** с блокирующего режима на асинхронный —
это уже правка UI и контракта. Заложив оба режима с самого начала, мы
получаем готовую основу и для бота, и для стриминга (этап 4): SSE станет
третьим способом наблюдать за тем же самым заданием.

Реализация асинхронного режима на этапе 2 — один `process.spawn` вокруг
`run_task`. Владельца задания (отслеживание, отмена, ретраи) не пишем:
требования к нему пока неизвестны, см. ниже.

### 10.4 Чего не делаем сейчас

**Супервизора под агентов.** Пока задания запускаются только из HTTP, он был
бы пустой обёрткой. Его реальная форма определяется требованиями, которых
ещё нет:

- нужно ли возобновлять задания после перезапуска сервера;
- нужна ли отмена задания на полпути;
- есть ли предел числа одновременных агентов и что делать при его достижении;
- нужны ли повторы при сбое провайдера.

Написать супервизор до ответов на эти вопросы — значит написать его дважды.
Благодаря 10.1–10.3 добавление обойдётся в один модуль: вся доменная логика
уже не зависит от того, кто её вызвал.

**Очереди заданий.** Ограничение «одно активное задание на сессию» (п. 8.4)
делает очередь ненужной, пока число сессий невелико.

## 11. Инструменты

Инструменты — то, ради чего существует многошаговость. Без них цикл агента
вырождается в один запрос к модели (п. 7.2).

### 11.1 Состав

Семь инструментов, сгруппированных по тому, чего они требуют от окружения.
Группировка не косметическая: от неё зависит, что нужно написать помимо
самой функции.

| Инструмент | Что делает | Требует |
|---|---|---|
| `now` | Текущее время, дата, часовой пояс | ничего |
| `calc` | Арифметика по строке выражения | ничего |
| `roll_dice` | Бросок кубика `NdM` | ничего |
| `find_task` | Поиск по прошлым заданиям этой сессии | доступ к своей БД |
| `read_file` | Чтение файла проекта | песочницу по пути |
| `http_request` | Запрос наружу | список разрешённых хостов |
| `call_agent` | Делегирование подзадачи другому агенту | защиту от рекурсии |

**Первые три** — чистые функции без побочных эффектов. Их задача не столько
прикладная, сколько проверочная: на них отлаживается весь механизм вызовов,
потому что они не могут сломаться по внешней причине. `roll_dice` вдобавок
проверяет случай, когда модель **обязана** вызвать инструмент: выдумать
честный бросок она не может.

**`find_task`** — первый шаг к памяти между заданиями (п. 12.1). Агент не
получает прошлый контекст автоматически, но может его найти, если сочтёт
нужным. Это дешевле полноценной памяти и не упирается в лимит контекста.

**Последние три** — опасные, разбираются ниже.

### 11.1.1 Что потребовалось сверх плана

**Миграция 4: `tool_calls_json` и `tool_call_id`.** Протокол OpenAI требует
вернуть модели её же вызовы вместе с результатами. Восстанавливать их из
`raw_response` на каждом шаге — лишняя хрупкость, поэтому они хранятся.

**`user_content` стал `Option`.** После вызова инструментов запрос
продолжает историю, и нового сообщения от пользователя в нём нет. Поначалу
цикл повторял задание на каждом шаге — реальная модель от этого пошла бы
на второй круг с тем же инструментом. Теперь задание отправляется один раз,
на первом шаге.

Строка-запрос при этом всё равно создаётся: в ней лежит `raw_request`, ради
которого каркас и строился. Её пустой текст — признак того, что шаг
инициирован циклом агента, а не человеком; в ленте он так и подписан:
«Агент → модель».

### 11.2 Как инструмент объявляется

Инструменты, как и каталог моделей, **вкомпилированы**, а не лежат в БД.
Это код, а не данные: у каждого есть реализация, и хранить рядом с ней
декларацию в базе означало бы риск расхождения.

Новый модуль `server/src/server/agent/tools.gleam` с реестром:

```gleam
pub type Tool {
  Tool(
    id: String,
    /// Описание для модели — от него зависит, догадается ли она вызвать.
    description: String,
    /// JSON Schema параметров, уходит в тело запроса.
    parameters: Json,
    /// Нужны ли инструменту БД и конфиг. Чистые функции получают Nil.
    run: fn(ToolContext, Dynamic) -> Result(Json, ToolError),
  )
}

pub fn registry() -> List(Tool)
```

`ToolContext` несёт соединение с БД и идентификаторы текущей сессии и
задания. На этапе 3b к ним добавились `sandbox` (ограничения из конфига),
`chain` (цепочка агентов от корня), `budget` (остаток шагов на всё дерево)
и `run_agent` — всё, что нужно `read_file`, `http_request` и `call_agent`.

### 11.3 Разрешения на уровне агента

У агента появляется список доступных ему инструментов:

```sql
ALTER TABLE agents ADD COLUMN tools_json TEXT;   -- ["now","calc"], NULL = нет
```

```gleam
pub type Agent {
  Agent(
    …,
    /// Идентификаторы из реестра. Пустой список — агент без инструментов.
    tools: List(String),
  )
}
```

По умолчанию список **пуст**. Включение `read_file` или `http_request`
должно быть осознанным действием, а не следствием невнимательности при
создании агента.

Неизвестный идентификатор при сохранении агента → `400 unknown_tool`.
Молча игнорировать нельзя: пользователь будет думать, что инструмент
подключён, и не поймёт, почему агент им не пользуется.

### 11.4 Опасные инструменты

**`read_file`.** Песочница обязательна. Корень задаётся переменной
окружения `AGENT_FILES_ROOT`; если она не задана, инструмент недоступен —
не «читает откуда угодно», а именно недоступен. Путь приводится к
каноническому виду и проверяется на принадлежность корню уже **после**
развёртывания `..` и символических ссылок. Проверять до — классическая
дыра.

Дополнительно: лимит размера файла (иначе один `read_file` съест весь
контекст) — `AGENT_MAX_FILE_BYTES`, по умолчанию 64 КБ.

> Канонизации пути не нашлось ни в стандартной библиотеке, ни в
> `simplifile`, поэтому добавлен FFI-модуль `server_path_ffi.erl`. Он
> разворачивает символические ссылки **посегментно, сверху вниз**, и
> схлопывает `..` уже после них: иначе `link/..` вёл бы не туда, куда
> показывает ссылка, а туда, где она лежит. Счётчик глубины (32) страхует
> от циклических ссылок `a → b → a`.
>
> Первая версия FFI разрешала ссылки, но не схлопывала `..` — и тест на
> `../../etc/passwd` показал, что проверка префикса проходит обманом.
> Ради этого тесты и пишутся.

Сравнение с корнем идёт **с разделителем** (`root <> "/"`), иначе каталог
`/srv/data-secret` считался бы находящимся внутри `/srv/data`.

**`http_request`.** Список разрешённых хостов в `AGENT_HTTP_ALLOWLIST`,
пустой по умолчанию. Таймаут 15 секунд, лимит размера ответа
`AGENT_MAX_HTTP_BYTES` (тело сверх него обрезается с пометкой). Запрет на
приватные диапазоны адресов (`127.0.0.0/8`, `10/8`, `172.16/12`,
`192.168/16`, `169.254/16`) — иначе агент получает доступ к внутренней
сети, включая собственный API сервера. Запрет действует даже на хост из
списка: туда он может попасть по недосмотру.

> Диапазон `172.16.0.0/12` легко задать неверно: префикс «172.» слишком
> широк (172.32 уже публичный), а перечислять 172.16…172.31 по одному
> некрасиво. Второй октет разбирается числом, на обе границы есть тесты.

**`call_agent`.** Самый интересный и самый опасный: агент А вызывает
агента Б, тот снова А — и так до исчерпания памяти.

Защита в три слоя:

1. **Предел глубины** — `AGENT_MAX_DEPTH`, по умолчанию 3. Длина цепочки
   в `ToolContext` растёт при каждом вложенном вызове.
2. **Обнаружение цикла** — в контексте хранится цепочка `agent_id` от
   корня; повторное появление идентификатора запрещено.
3. **Общий бюджет шагов** — `max_steps` считается по всему дереву вызовов,
   а не на каждом уровне отдельно. Иначе три агента по пять шагов дадут
   сто двадцать пять обращений к LLM.

Отказ по любой из трёх причин — обычный результат инструмента со
`status = error`, а не крах задания: модель читает объяснение и решает,
что делать дальше.

Вложенный запуск создаёт **свою сессию** с заголовком вида
«Второй ← Первый». Так вложенная работа видна в интерфейсе как обычный
запуск, и наблюдаемость не теряется — а это главная ценность проекта.
Цепочка читается прямо из списка сессий: `Ц2 ← Ц1 ← Корень`.

> Инструменту нужен запуск агента, а запуск агента вызывает инструменты.
> Прямая ссылка дала бы циклическую зависимость модулей, которой Gleam не
> допускает, поэтому `tools.ToolContext` получает поле `run_agent` типа
> `Delegate` — функцию, которую подставляет `loop`. Заодно это упрощает
> юнит-тесты: там вместо цикла стоит заглушка.

### 11.5 Что меняется в точках расширения

Здесь каркас проходит настоящую проверку: инструменты задевают **обе**
точки, и обе — только изнутри.

**★1 `build_request_body`.** Добавляется поле `tools` в теле запроса, если
список непуст. Берётся из `RequestContext`, который уже расширяется под
историю (п. 6). Сигнатура не меняется.

**★2 `parse_response_body`.** Появляется разбор `tool_calls` в ответе.
Результат разбора расширяется:

```gleam
pub type ParsedResponse {
  /// Модель ответила текстом — задание завершено.
  TextAnswer(content: String, reasoning: Option(String), usage: …)
  /// Модель просит вызвать инструменты — нужен ещё шаг.
  ToolCalls(calls: List(ToolCall), usage: …)
}
```

Это и есть честный признак завершения, которого не хватало в п. 7.2:
`TextAnswer` — выход из цикла, `ToolCalls` — продолжение.

**★3 `client.send`.** Не меняется.

### 11.6 Роль `tool` и единственная правка клиента

Формат OpenAI требует роли `tool` для результатов вызова. Значит в
`shared/types.gleam`:

```gleam
pub type Role {
  System
  User
  Assistant
  Tool          // ← новый
}
```

**Это единственное место во всей переделке, где правка `shared` задевает
клиент.** В `client/src/client/ui/dialog.gleam` два исчерпывающих `case` по
роли — компилятор на них укажет, нужно добавить по ветке (CSS-класс и
подпись «Инструмент»).

Полагаться на запасной вариант декодера нельзя: `role_decoder` подставляет
`User` для неизвестных значений, и результаты вызовов молча отрисовались бы
как сообщения пользователя. Молчаливое искажение хуже ошибки компиляции.

Контрактный тест при этом остаётся зелёным: он проверяет наличие поля
`role`, а не множество его значений.

### 11.7 Наблюдаемость вызовов

Каждый вызов инструмента — строка в `messages` с `role = "tool"`,
заполненными `raw_request` (аргументы) и `raw_response` (результат). То
есть существующая кнопка `{} JSON` работает для инструментов без правок,
а в ленте вызов выглядит как ещё один шаг внутри задания.

Ошибка инструмента не прерывает задание: она возвращается модели как
результат вызова, чтобы та могла исправиться. В БД такой шаг помечается
`status = error` — видно, что пошло не так, но цикл продолжается.

Это та же логика, по которой ошибка провайдера становится сообщением, а не
HTTP-ошибкой.

### 11.8 Порядок реализации

Инструменты разворачиваются двумя подэтапами:

- **3a** — механизм плюс три чистых инструмента (`now`, `calc`,
  `roll_dice`). Здесь отлаживается цикл, роль `tool`, лента и разбор
  `tool_calls`. Ничего внешнего, поэтому ошибки однозначны.
- **3b** — остальные четыре, каждый со своими ограничениями.

`call_agent` делается последним: он опирается на уже работающий цикл.

## 13. Принятые решения и отложенное

### 13.1 Решено

- **Статус — у задания, а не у сессии** (п. 2.1). Снимает вопрос
  «долгоживущий диалог или одноразовая задача»: сессия копит задания,
  каждое из которых одноразово.
- **Удаление отдельного шага запрещено.** Внутри задания шаги связаны
  историей: удалив шаг 2, получим невоспроизводимое задание. Удаляется
  задание целиком. Для сессий без агента удаление пары работает как
  сейчас.
  Реализовано на обоих уровнях: `DELETE` шага отвечает
  `409 message_belongs_to_task`, и у шагов нет кнопки `×` в ленте.
  Защита только в интерфейсе была бы иллюзией — API остаётся открытым.
- **`seq` и `step` сосуществуют.** `seq` сквозной по сессии (на нём держится
  существующий код), `step` локальный для задания. Дублирование осознанное.
- **`shared` меняется только добавлением** (п. 4.2). Единственное
  исключение — роль `tool` (п. 11.6), и оно разбирается компилятором.

### 13.2 Отложено

**Память между заданиями.** Сейчас каждое задание начинается с чистого
листа: `history` — это шаги внутри текущего задания, не более. Агент может
дотянуться до прошлого через `find_task` (п. 11.1), если сочтёт нужным.

Когда понадобится настоящая память, выбирать придётся между тремя
вариантами: вся история сессии, только пары «задание → итог», или
суммаризация старого. Третий правильнее остальных, но требует стратегии
вытеснения и отдельного вызова LLM. Решать это заранее незачем — `find_task`
закрывает большую часть потребности почти бесплатно.

Важно: структура уже готова. `tasks` хранит `prompt` и `result`, поэтому
любой из трёх вариантов реализуется без миграции.

**Шаблоны агентов.** Предустановленных агентов нет, список при первом
запуске пуст — экран агентов (п. 15) объясняет это подсказкой. Если понадобятся — это миграция с данными либо, что лучше,
кнопка «создать из примера» в интерфейсе: тогда примеры остаются кодом и не
попадают в чужие базы.

**Супервизор и внешние каналы** — см. п. 10.4. Ядро к ним готово,
но писать до появления требований нечего.

## 14. Наблюдение в реальном времени (этап 4)

Единственный этап, который меняет контракт. Поэтому отдельный раздел.

### 14.1 Что именно не так сейчас

Задание из пяти шагов выполняется полторы минуты, и всё это время
интерфейс показывает крутилку. Шаги уже сохранены в БД и доступны через
`GET /api/tasks/:id`, но увидеть их можно, только дождавшись конца.

Это обидно вдвойне: **наблюдаемость — главная ценность проекта**, ради неё
сохраняются все сырые тела. А самый интересный момент — как агент
рассуждает по дороге — остаётся невидимым.

### 14.2 Два разных стриминга

Слово «стриминг» означает здесь две независимые вещи, и их важно
разделить, иначе этап расползётся.

| | Что даёт | Чего стоит |
|---|---|---|
| **А. Поток шагов** | Шаг появляется в ленте, как только завершён | Один SSE-эндпоинт, транспорт не трогаем |
| **Б. Поток токенов** | Текст ответа набирается по буквам | Переписывание ★3, разбор SSE провайдера, частичные строки в БД |

**Делаем А, не делаем Б.** Причина не в трудоёмкости, а в том, что Б
разрушает свойство, на котором держится весь каркас: «в БД лежит ровно то,
что ушло и пришло». Частичный ответ — это не сырое тело, его нечем
проверить и не с чем сравнить.

Выгода при этом несимметрична: А превращает полторы минуты тишины в
видимую работу, Б лишь украшает последние пять секунд. Шаг — естественная
единица наблюдения за агентом, как сообщение — за чатом.

> Отсюда следует, что ★3 `send` **не меняется и на этом этапе**, а
> `send_streaming` из п. 6 не нужен вовсе. Запись в п. 6 устарела: она
> писалась, когда А и Б ещё не были разделены.

### 14.3 Эндпоинт

```
GET /api/sessions/:id/events      → text/event-stream
```

События сессии, а не задания. Так подписка переживает смену заданий:
клиент открывает её один раз при входе в сессию и не переподключается на
каждое задание.

```jsonc
// event: step      — завершён шаг
{ "task_id": "tsk_…", "step": 2, "messages": [ /* Message */ ] }

// event: task      — задание изменило состояние
{ "task": { "id": "tsk_…", "status": "done", "result": "…", "steps": 3 } }

// event: ping      — раз в 30 секунд, чтобы прокси не закрыл соединение
{}
```

Полные объекты, а не идентификаторы: иначе на каждое событие клиент
отвечал бы запросом, и мы получили бы ту же задержку плюс лишний трафик.
Декодеры для них уже есть — те же, что у `GET /api/tasks/:id`.

### 14.4 Как события попадают в поток

Главная сложность: цикл агента крутится в одном процессе, SSE-соединение
живёт в другом, и знать друг о друге они не должны. Цикл не импортирует
`wisp` и `mist` (п. 10.1) — это свойство терять нельзя.

Решение — **шина событий**: именованный процесс, который принимает
публикации и рассылает их подписчикам.

```gleam
// server/src/server/events.gleam — не знает ни про HTTP, ни про агентов
pub type Event {
  StepFinished(session_id: String, task_id: String, step: Int)
  TaskChanged(session_id: String, task_id: String)
}

pub fn publish(event: Event) -> Nil
pub fn subscribe(session_id: String, subject: Subject(Event)) -> Nil
```

`publish` возвращает `Nil`, а не `Result`: цикл агента не должен
прерываться из-за того, что шина не поднялась. Наблюдение — удобство,
работа агента — суть.

Имя шины берётся из крошечного FFI (`server_events_ffi.erl`), а не из
`process.new_name`: последняя порождает новый атом при каждом вызове, и
звать её из `publish` значило бы заполнять таблицу атомов. Фиксированный
атом позволяет публиковать событие откуда угодно, не протаскивая
`Subject` через всю цепочку вызовов.

Цикл зовёт `events.publish` и продолжает работу, не интересуясь, слушает
ли кто-нибудь. Если не слушает никто — публикация ничего не стоит.

**Порядок важен: сначала запись в БД, потом публикация.** Подписчик читает
данные из базы, поэтому объявить раньше значило бы отправить его к пустому
результату. По той же причине шаг с вызовом инструментов объявляется
только после того, как дописаны их результаты, — иначе он ушёл бы к
клиенту наполовину.

**В событии только идентификаторы, тело читает подписчик.** Иначе цикл
собирал бы JSON для каждого соединения, в том числе когда их ноль.
Источник правды остаётся в БД (п. 10.2), а шина лишь говорит «посмотри
туда» — поэтому пропущенное событие не теряет данные, а приводит к тому,
что клиент узнает о шаге чуть позже.

### 14.5 Отказ подписчика не ломает агента

Браузер закрывают посреди задания — это норма, а не сбой.

Шина **не связывается** с подписчиками через `link`: упавший процесс
соединения не должен ронять цикл агента. Мёртвые подписки убираются
лениво, при следующей рассылке: `send` мёртвому процессу в Erlang
безвреден, поэтому отдельный монитор здесь — усложнение без выгоды.

### 14.6 Стык mist и wisp

SSE требует mist напрямую: `mist.server_sent_events` работает с
`Request(mist.Connection)`, а wisp этот тип уже спрятал.

Значит, в `server.gleam` маршрут раздваивается **до** wisp:

```gleam
fn handle(request: Request(mist.Connection)) -> Response(mist.ResponseData) {
  case request.path_segments(request) {
    // Единственный путь, который до wisp не доходит.
    ["api", "sessions", id, "events"] -> sse.handle(request, context, id)
    _ -> wisp_handler(request)
  }
}
```

Это единственное место, где слои смешиваются, и оно того стоит: SSE —
принципиально другой вид ответа, который wisp не моделирует. Весь
остальной API продолжает жить в `router.gleam` без изменений.

### 14.7 Что меняется у клиента

`EventSource` — часть браузера, обёртка в FFI на десяток строк. Поток
подключается к существующему `Msg`, не заменяя загрузку:

```gleam
StepArrived(task_id: String, messages: List(Message))
TaskUpdated(task: Task)
StreamFailed
```

Три правила, без которых получится хуже, чем было:

1. **Поток дополняет опрос, а не заменяет.** При открытии сессии данные
   по-прежнему грузятся запросом: SSE даёт изменения, а не состояние.
2. **Идемпотентность.** Шаг, пришедший и потоком, и в ответе на
   `POST /tasks`, не должен удваиваться — слияние по `id` сообщения.
3. **Отвал незаметен.** `EventSource` переподключается сам; на время
   обрыва остаётся прежнее поведение — результат придёт с ответом.

Переход на `?async=true` в UI **не делаем**. Соблазн есть: раз шаги видны,
блокирующий запрос не нужен. Но тогда завершение задания узнаётся только
из потока, и обрыв связи оставляет интерфейс в подвешенном состоянии
навсегда. Синхронный запрос остаётся страховкой, а SSE — ускорением.

**Выполняющееся задание разворачивается само.** Шаги по-прежнему свёрнуты
по умолчанию, но пока итога нет, смотреть больше не на что — свёрнутая
карточка показывала бы ровно ту крутилку, от которой этап и избавляет.
Как только задание завершилось, действует обычное правило: виден итог,
шаги разворачиваются по требованию.

### 14.8 Контракт

Это добавление, а не изменение: существующие эндпоинты отвечают как
прежде. Оба контрактных теста (`api_contract`, `agents_contract`) обязаны
остаться зелёными **без правок** — то же требование, что на этапах 0–3.

Новый тест `e2e/13_events_test.mjs` проверяет поток отдельно: обычным
`fetch` с чтением тела по частям, без браузерного `EventSource`.

| Проверка | Почему именно она |
|---|---|
| Заголовки `text/event-stream`, `no-cache` | Без них прокси буферизует поток, и весь этап теряет смысл |
| Шаг приходит **до** ответа на `POST /tasks` | Собственно то, ради чего всё делается |
| Формат события разбирается теми же декодерами | Иначе контракт расходится с остальным API |
| События чужой сессии не приходят | Утечка данных между сессиями |
| Обрыв подписчика не ломает задание | Браузер закрывают посреди работы — это норма |
| `ping` в простое | Доказывает, что соединение держится |

### 14.9 Чего не делаем

- **Поток токенов** (вариант Б) — см. 14.2.
- **Воспроизведение пропущенного** (`Last-Event-ID`). Клиент после
  переподключения дочитывает состояние обычным запросом — это проще и
  надёжнее, чем хранить буфер событий на сервере.
- **Отмену задания через поток.** SSE однонаправлен; отмене место в
  `DELETE /api/tasks/:id`, и она ждёт требований вместе с супервизором
  (п. 10.4).

### 14.10 Найденное при реализации

- **Автовыбор сессии не открывал поток.** Подписка стояла на явном выборе
  сессии в списке, а первая сессия выбирается при загрузке сама, минуя
  этот путь. В итоге поток работал везде, кроме самого частого случая —
  открыть приложение и смотреть на то, что уже открыто. Поймано
  UI-тестом; в ручной проверке незаметно, потому что достаточно один раз
  кликнуть по соседней сессии.
- **Шаг объявлялся до выполнения инструментов.** Публикация стояла сразу
  после записи ответа модели, а строки с ролью `tool` дописываются после.
  Подписчик при этом видел шаг наполовину. Исправлено переносом
  публикации в конец обработки шага — на всех трёх путях: обычный ответ,
  вызовы инструментов, ошибка провайдера.
- **Проверка «шаг раньше ответа» измеряла шум.** Мок отвечает мгновенно,
  всё задание занимало десятки миллисекунд, и сравнение времён давало
  случайный результат. В мок добавлен сценарий «не спеша» с паузой на
  втором шаге: теперь шаг опережает ответ на ~1,2 секунды, и проверка
  говорит о поведении, а не о планировщике.
- **happy-dom не реализует `EventSource`.** В харнессе появилась
  подстановка поверх `fetch` — протокол тот же, и проверяется именно
  клиентский код, а не браузерный API.

## 15. Экран агентов

Этапы 1–4 оставили интерфейс почти нетронутым: ТЗ требовало менять его по
минимуму. Следствие оказалось неудобным — агента нельзя было создать из
браузера, только через `POST /api/agents`. Бэкенд умел всё, дотянуться до
него было нечем.

### 15.1 Что добавлено

Кнопка **«Агенты»** в боковой панели открывает экран поверх диалога.
Перекрывает целиком, а не делит пространство: настройка и переписка нужны
не одновременно.

- **Список** — имя, модель коротким именем, число запусков. Кнопки
  «Запустить», «Настроить», «Удалить».
- **Форма** — имя, описание, системный промпт, провайдер и модель,
  предел шагов, чекбоксы инструментов.
- **Запуск** создаёт сессию и сразу её открывает: экран закрывается, в
  composer появляется «Выдать задание».

### 15.2 Решения

**Валидацию не дублируем.** Сервер уже проверяет имя, модель и пределы
`max_steps`, и его сообщения точнее. На клиенте только то, что нельзя
выразить запросом: пустое имя блокирует кнопку.

**Параметры (`temperature` и прочие) в форме агента не правятся.** Форма
и так длинная, а поля те же, что в панели `⚙` сессии. Агент хранит их как
значения по умолчанию, запуск переопределяет по полю — этого достаточно.

**Полная карточка догружается отдельным запросом.** Список отдаёт только
имя и модель: тащить промпт и параметры ради возможной правки — лишний
трафик. Нажатие «Настроить» делает `GET /api/agents/:id`.

**Инструменты — чекбоксы с описаниями, а не мультиселект.** Описание
важнее компактности: от него зависит, догадается ли модель вызвать
инструмент. Предупреждение о доступе к файлам и сети стоит **над**
списком — после семи строк его уже не прочитают.

### 15.3 Найденное при реализации

- **`attr("checked", "")` отмечает чекбокс.** Пустое значение не делает
  атрибут отсутствующим — все семь инструментов выглядели выбранными.
  Нужен `attribute.checked(Bool)`, который умеет атрибут убирать.
  Поймано не тестом, а скриншотом: в DOM-проверке я смотрел на состояние
  модели, а не на разметку.
- **`gleam format` откатывает правку, если запущен в той же команде.**
  Дважды потерял изменение, пока не заметил, что проверяю собранный
  бандл, а не исходник. Привычка `grep -c` по результату сборки оказалась
  полезнее, чем доверие к «файл записан».

### 15.4 Контракт

Ни одного нового эндпоинта: экран пользуется тем, что было сделано на
этапе 1 и лежало без применения. В `shared` добавлен единственный тип
`ToolInfo` — разбор `GET /api/tools`, который раньше читал только тест.

Оба контрактных теста остались зелёными без правок.

## 16. Память агента

Раздел 13.2 откладывал память между заданиями: `find_task` закрывал
большую часть потребности почти бесплатно. Практика показала обратное —
агент забывал предыдущий разговор, и пользователю приходилось повторять
контекст в каждом задании.

### 16.1 Слои, а не режимы

Ключевое решение: перечисленные способы — **не альтернативы**. Они
складываются, и запрещать сочетания незачем.

```
системный промпт  ← кто агент
+ факты           ← что он знает об этом запуске
+ пересказ        ← сжатое изложение вытесненного
+ окно            ← последние N заданий как есть
+ текущее задание ← шаги, идущие прямо сейчас
```

Поэтому настройка — четыре независимых переключателя, а не один селект.

```gleam
pub type Memory {
  Memory(
    window: MemoryWindow,
    summary: SummaryMode,
    facts: Bool,
    budget_chars: Int,
  )
}

pub type MemoryWindow {
  NoMemory
  Outcomes(tasks: Int)      // пары «задание → итог», без шагов
  Transcripts(tasks: Int)   // последние N заданий целиком
  Everything
}
```

**`Outcomes` и `Transcripts` разделены** потому, что это разная цена за
разную точность: итог задания — абзац, полная расшифровка с вызовами
инструментов — десятки килобайт. Для «не терять нить» хватает первого.

### 16.2 Бюджет — последний рубеж

Любая комбинация рано или поздно переполнит контекст, и провайдер
отвергнет запрос **целиком**. Поэтому поверх окна всегда работает
предел: история режется с головы, пока не влезет.

Точный подсчёт токенов требует токенизатора, которого нет. Оценка
«4 символа ≈ токен» занижена намеренно — лучше отправить меньше, чем
получить отказ. Умолчание — четверть `context_length` модели: остальное
нужно промпту, заданию, описаниям инструментов и самому ответу.

**Режется только окно.** Факты и пересказ не вытесняются — ради них
память и нужна. Текущее задание тем более.

### 16.3 Пересказ

Единственный слой, который **обращается к модели**: стоит денег, занимает
время и может не получиться. Поэтому живёт в отдельном модуле
(`agent/summarize.gleam`) — у него другая цена ошибки.

- **Когда.** Накопилось `SummarizeEvery(n)` сообщений, не вошедших в
  прошлый пересказ.
- **Как.** Предыдущий пересказ подаётся на вход новому: пересказывается
  пересказ, а не вся история заново. Иначе каждое сжатие стоило бы
  дороже предыдущего.
- **Где.** Синхронно, **до** сборки запроса: иначе свежий пересказ
  применился бы только к следующему заданию.

Два свойства, которые важно не потерять:

**Пересказ не трогает `messages`.** Исходные шаги остаются в БД со всеми
сырыми телами — наблюдаемость не страдает. Сжимается только то, что
подставляется в запрос.

**Запрос сжатия идёт мимо `chat.send`** и не попадает в ленту. Иначе
служебный вызов выглядел бы шагом задания и путал бы картину наблюдения.

Неудача сжатия не срывает задание: агент получит менее полную память —
это хуже, чем могло быть, но лучше упавшего задания.

### 16.4 Факты

Инструменты `remember` и `forget`, таблица `facts`, привязка к сессии.

К сессии, а не к агенту: у агента для постоянных знаний есть системный
промпт, а факт — то, что выяснилось в конкретном запуске.

Подставляются ролью `system`, а не `user`: это знание об обстановке, а не
реплика в диалоге. Повторы игнорируются — модель склонна повторять
«запомни» на каждом шаге, и без защиты список забился бы дублями.

`forget` работает по подстроке, а не по идентификатору: модель оперирует
содержанием, а не `fct_…`. Возвращает число удалённых — ноль не ошибка,
но агенту полезно знать, что ничего не совпало.

### 16.5 Токены

| Где | Откуда | Точность |
|---|---|---|
| Запрос, ответ, диалог | `usage` провайдера | точно |
| Решение «резать или нет» | оценка `len / 4` | приблизительно |

Первое уже лежало в БД, просто не показывалось сводно. `GET
/api/sessions/:id/memory` отдаёт факты, пересказ и расход вместе — одной
панелью они и показываются.

### 16.6 Найденное при реализации

- **Пустые `user` уходили провайдеру.** У шага, инициированного циклом,
  текст запроса пуст: строка существует ради `raw_request` в БД.
  В теле запроса между результатом инструмента и следующим ответом
  появлялось пустое `user` — модель оно только сбивало. Баг был и до
  памяти, просто история до неё была короткой.
- **Фильтр по статусу сломал делегирование.** Убирая пустые строки,
  я заодно отбросил сообщения со `status = error`. Но неудачный вызов
  инструмента помечен именно так — и модель переставала видеть отказ,
  просила то же самое снова и упиралась в лимит шагов. **Отказ — это
  ответ, а не отсутствие ответа.** Поймано контрактным тестом
  `12_sandbox`, который до этого был зелёным полтора этапа.
- **Мок выбирал сценарий по первому `user`-сообщению.** С появлением
  памяти первыми стали идти прошлые задания, и мок отвечал по чужому
  тексту. Исправлено на «последнее сообщение пользователя» — текущее
  задание всегда последнее.

### 16.7 Отложено

**Асинхронное сжатие.** Сейчас оно синхронное: задание ждёт. Асинхронно
было бы приятнее, но тогда задание уходит с неполной памятью, и
поведение становится недетерминированным — одно и то же задание даёт
разный результат в зависимости от того, успело ли сжатие.

**Память для вложенных агентов.** `call_agent` создаёт свою сессию,
значит у подагента своя память, и родительскую он не видит. Так и
правильно: ему дают конкретную подзадачу, а не пересказ чужого разговора.
