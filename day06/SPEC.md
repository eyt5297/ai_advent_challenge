# ТЗ: LLM-чат на Gleam + Lustre + SQLite

Версия: 1.0 (каркас / MVP)
Дата: 2026-11-13

---

## 1. Цель

Создать **каркас** веб-приложения для общения с LLM через HTTP API нескольких
провайдеров.

Ключевая задача этапа — не богатый функционал, а **архитектура**: весь код,
который отвечает за «как собрать запрос» и «как разобрать ответ», должен быть
изолирован в отдельных, явно названных функциях с чётким контрактом. Дальнейшее
развитие (история диалога, стриминг, tools, вложения) должно сводиться к правке
этих функций, без изменения UI, БД и транспорта.

## 3. Провайдеры и модели

### 3.1 Провайдеры

Оба провайдера — OpenAI-совместимые (`POST /chat/completions`), различаются
только base URL, переменной с ключом и списком моделей.

| id | Название | Base URL | Env-переменная ключа |
|---|---|---|---|
| `veai` | VeAI | `https://api.veai.ru/openai/api/v1` | `OPENAI_API_KEY` |
| `kimi` | Kimi | `https://api.kimi.ai/coding/v1` | `KIMI_API_KEY` |

Base URL каждого провайдера переопределяется env-переменными
`VEAI_BASE_URL` / `KIMI_BASE_URL` — чтобы не трогать код при смене эндпоинта.

Если ключ провайдера не задан в окружении — провайдер отдаётся клиенту с
флагом `available: false` и в выпадающем списке отображается как disabled.

### 3.2 Каталог моделей

Хардкод в `shared/catalog.gleam`:

```gleam
pub type Provider {
  Provider(
    id: String,
    title: String,
    groups: List(ModelGroup),   // для <optgroup>
    default_model: String,
  )
}

/// Группа моделей внутри провайдера (вендор или «Авто»).
pub type ModelGroup {
  ModelGroup(title: String, models: List(ModelInfo))
}

pub type ModelInfo {
  ModelInfo(
    id: String,                  // то, что уходит в поле "model" запроса
    title: String,               // подпись в списке
    context_length: Int,         // 0 = неизвестно
    max_output_tokens: Int,      // 0 = неизвестно
    vision: Bool,                // принимает изображения
    tools: Bool,                 // поддерживает tool calls
    reasoning: ReasoningSupport,
  )
}

/// Поддержка «рассуждений» конкретной моделью.
pub type ReasoningSupport {
  /// Модель не рассуждает (haiku-4.5, gemini-3.5-flash-lite).
  NoReasoning
  /// Рассуждения можно включать/выключать и задавать усилие.
  OptionalReasoning(
    default_enabled: Bool,
    default_effort: String,
    efforts: List(String),
  )
  /// Модель рассуждает всегда, можно только менять усилие (все модели kimi).
  AlwaysReasoning(default_effort: String, efforts: List(String))
}
```

У veai 36 моделей — плоский `select` неудобен, поэтому каталог двухуровневый.
У kimi одна группа, её заголовок в UI не рисуется.

### 3.3 Reasoning: различия провайдеров

Это главное расхождение между провайдерами, и каркас обязан его инкапсулировать.

| | veai | kimi |
|---|---|---|
| Поле в ответе API | `reasoning` | `think_efforts` / `reasoning` |
| Обязательность | `mandatory: false`, `default_enabled: true` | `supports_thinking_type: "only"` — **всегда** |
| Шкала усилий | `low`, `medium`, `high`, `xhigh`, `max` | `low`, `high`, `max` |
| Усилие по умолчанию | `medium` | `high` (у `kimi-for-coding` — `max`) |
| Модели без reasoning | `haiku-4.5`, `gemini-3.5-flash-lite` | нет |

Практические следствия:

1. **Шкала усилий хранится в каталоге** (`ReasoningSupport.efforts`), а не
   хардкодится. Когда усилие появится в UI, список значений будет
   подставляться под выбранную модель, а не быть общим.
2. **`parse_response_body` обязана пережить поле с рассуждениями** рядом с
   `content` (`reasoning_content` или аналог). В MVP берём только `content`;
   рассуждения складываем в `ParsedResponse.reasoning` и пока не показываем —
   но они всегда видны в разворачивающемся сыром JSON.
3. **`RequestOptions.reasoning_effort: Option(String)`** в MVP всегда `None`
   и в тело запроса не попадает — берётся дефолт провайдера. Включение
   сведётся к одной строке в `build_request_body`.

### 3.4 Регенерация каталога

`shared/catalog.gleam` — сгенерированный файл, правится не руками, а
скриптом `scripts/gen_catalog.sh`:

```
curl -s $VEAI_BASE_URL/models -H "Authorization: Bearer $OPENAI_API_KEY" > modeles.txt
curl -s $KIMI_BASE_URL/models -H "Authorization: Bearer $KIMI_API_KEY"   > kimi_models.txt
# jq-шаблон -> shared/src/shared/catalog.gleam
```

Так список остаётся актуальным одной командой, но на рантайме сетевых
запросов за каталогом нет — он вкомпилирован. Сырые ответы провайдеров
(`modeles.txt`, `kimi_models.txt`) держим в репозитории как справочник
по возможностям моделей.

## 4. Модель данных (SQLite)

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS sessions (
  id           TEXT PRIMARY KEY,          -- uuid v4
  title        TEXT NOT NULL,             -- "Новый чат" -> первые 60 симв. 1-го сообщения
  created_at   INTEGER NOT NULL,          -- unix ms
  updated_at   INTEGER NOT NULL,
  provider_id  TEXT,                      -- последний выбранный, для восстановления UI
  model_id     TEXT,
  params_json  TEXT                       -- RequestOptions сессии, см. п.4.1
);

CREATE TABLE IF NOT EXISTS messages (
  id            TEXT PRIMARY KEY,         -- uuid v4
  session_id    TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  seq           INTEGER NOT NULL,         -- номер внутри сессии, присваивает INSERT
  role          TEXT NOT NULL,            -- 'user' | 'assistant' | 'system' | 'tool'
  content       TEXT NOT NULL,            -- извлечённый текст для показа
  provider_id   TEXT,
  model_id      TEXT,
  status        TEXT NOT NULL,            -- 'pending' | 'ok' | 'error'
  error         TEXT,                     -- текст ошибки, если status='error'
  params_json   TEXT,                     -- параметры, с которыми ушёл ЭТОТ запрос
  raw_request   TEXT,                     -- сырой JSON, который ушёл провайдеру
  raw_response  TEXT,                     -- сырое тело ответа провайдера
  http_status   INTEGER,
  latency_ms    INTEGER,
  reply_to      TEXT REFERENCES messages(id),  -- у ответа: id его запроса
  created_at    INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_messages_session
  ON messages(session_id, seq);

-- Страховка от гонки: номер присваивается внутри INSERT, но индекс
-- превращает возможный промах в явную ошибку, а не в порчу данных.
CREATE UNIQUE INDEX idx_messages_seq ON messages(session_id, seq);
CREATE INDEX idx_messages_reply ON messages(reply_to);
```

**Почему `reply_to`, а не соседний `seq`.** При параллельных отправках
между запросом и его ответом вклиниваются чужие строки, и номера пары
перестают быть соседними. Связь поэтому хранится, а не вычисляется.

### 4.1 Хранение параметров запроса

`params_json` в обеих таблицах — сериализованный `RequestOptions` (см. п. 6.1):

```jsonc
{
  "temperature": 0.7,          // null = не слать параметр вообще
  "max_tokens": 4096,
  "system_prompt": "…",
  "reasoning_enabled": true,
  "reasoning_effort": "medium",
  "stream": false
}
```

Два уровня намеренно:

- `sessions.params_json` — **текущая настройка сессии**, восстанавливается
  при её открытии. Пользователь настроил температуру один раз и она держится.
- `messages.params_json` — **снимок на момент отправки**, неизменяемый.
  Нужен, чтобы через неделю понять, с какими параметрами получен конкретный
  ответ, и чтобы кнопка «повторить» могла воспроизвести запрос один в один.

`null` у поля означает «не включать ключ в тело запроса» — это не то же самое,
что значение по умолчанию. Так мы отличаем «пользователь явно выставил
`temperature: 0`» от «параметр не трогали, пусть решает провайдер».

### Решения по хранению

- **Одна таблица `messages`** на запрос и ответ (две строки: `user` и
  `assistant`), связанные через `session_id` + соседние `seq`. Это оставляет
  дверь открытой для будущего мультитёрнового диалога: включить историю =
  просто начать читать предыдущие строки в `build_request_body`.
- `raw_request` хранится у строки `user`, `raw_response` — у строки
  `assistant`. Ошибка провайдера тоже создаёт строку `assistant` со
  `status='error'`, с сохранённым сырым телом — его видно в раскрывающемся
  JSON.
- Сырые JSON-ы хранятся **как есть, строкой**. Форматирование (pretty-print)
  делается на клиенте при разворачивании — БД не распухает отступами.
- Миграции — простой список SQL-строк в `db.gleam`, применяемых по порядку,
  с таблицей `schema_migrations(version INTEGER PRIMARY KEY)`.
- Удаление сессии каскадом удаляет сообщения.

## 5. Внутреннее HTTP API (client ↔ server)

Все тела — JSON, все ошибки — `{ "error": { "code": "...", "message": "..." } }`.

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/catalog` | Список провайдеров и моделей + флаг `available` |
| `GET` | `/api/sessions` | Список сессий (id, title, updated_at), новые сверху |
| `POST` | `/api/sessions` | Создать сессию. Тело: `{ "title": "..."? }` → сессия |
| `PATCH` | `/api/sessions/:id` | Переименовать и/или сохранить выбор модели и параметры: `{ "title"?, "provider_id"?, "model_id"?, "params"? }` |
| `DELETE` | `/api/sessions/:id` | Удалить сессию и её сообщения |
| `DELETE` | `/api/sessions/:id/messages/:mid` | Удалить обмен (запрос + ответ). Возвращает `{ "deleted": [id, …] }` |
| `GET` | `/api/sessions/:id/messages` | Все сообщения сессии по возрастанию `seq` |
| `POST` | `/api/sessions/:id/preview` | **Не отправляя**, собрать и вернуть JSON запроса (для редактора) |
| `POST` | `/api/sessions/:id/send` | Отправить запрос провайдеру, вернуть пару сообщений |
| `GET` | `/` , `/static/*` | SPA и статика |

Эндпоинты агентов (`/api/agents`, `/api/tasks`) описаны в
[SPEC_AGENTS.md](SPEC_AGENTS.md), п. 5. Перечисленные здесь работают
по-прежнему: сессия без агента остаётся допустимой и ведёт себя так же,
как до переделки.

### 5.1 `POST /api/sessions/:id/preview`

```jsonc
// request
{
  "provider_id": "veai",
  "model_id": "Anthropic/sonnet-5",
  "content": "привет",
  "params": { "temperature": 0.7, "max_tokens": 4096, "reasoning_effort": "medium" }
}
// response
{
  "raw_request": "{\n  \"model\": \"Anthropic/sonnet-5\",\n  \"messages\": [...]\n}",
  // params после normalize_options — UI показывает, что реально ушло
  "effective_params": { "temperature": 0.7, "max_tokens": 4096,
                        "reasoning_enabled": true, "reasoning_effort": "medium" },
  // предупреждения нормализации, если значения правились
  "warnings": ["effort 'xhigh' не поддерживается kimi, заменён на 'high'"]
}
```

### 5.2 `POST /api/sessions/:id/send`

```jsonc
// request — одно из двух:
{ "provider_id": "veai", "model_id": "...", "content": "привет",
  "params": { … } }
// либо, если пользователь отредактировал JSON вручную
// (params игнорируются — в override они уже вшиты):
{ "provider_id": "veai", "model_id": "...", "content": "привет",
  "raw_request_override": "{ ... валидный JSON ... }" }

// response
{
  "user": { /* Message */ },
  "assistant": { /* Message */ }
}
```

`raw_request_override` отправляется провайдеру **как есть** (сервер лишь
валидирует, что это разбираемый JSON). Это даёт «возможность отредактировать
отправляемый JSON» без ограничений на структуру.

## 6. Точки расширения (главное требование)

Три функции с замороженной сигнатурой. Вся будущая работа — внутри них.

### 6.1 `server/llm/request.gleam`

```gleam
/// Контекст, из которого собирается тело запроса.
/// Сейчас history игнорируется (режим «запрос-ответ»),
/// но поле уже есть — включение истории не меняет сигнатуру.
pub type RequestContext {
  RequestContext(
    provider: Provider,
    model_id: String,
    user_content: String,
    history: List(Message),      // пока всегда []
    options: RequestOptions,
  )
}

/// Параметры генерации. None = ключ не попадает в тело запроса.
pub type RequestOptions {
  RequestOptions(
    temperature: Option(Float),
    max_tokens: Option(Int),
    system_prompt: Option(String),
    reasoning_enabled: Option(Bool),
    reasoning_effort: Option(String),
    stream: Bool,                     // в MVP всегда False
  )
}

/// Дефолт: ничего не навязываем провайдеру.
pub fn default_options() -> RequestOptions {
  RequestOptions(None, None, None, None, None, False)
}

/// ★ ТОЧКА РАСШИРЕНИЯ №1
/// Собирает JSON-тело запроса к провайдеру.
pub fn build_request_body(ctx: RequestContext) -> json.Json
```

Текущая реализация (MVP) — минимум плюс заданные параметры:

```json
{
  "model": "Anthropic/sonnet-5",
  "messages": [
    { "role": "system", "content": "…" },
    { "role": "user", "content": "привет" }
  ],
  "temperature": 0.7,
  "max_tokens": 4096,
  "reasoning": { "enabled": true, "effort": "medium" }
}
```

Правила сборки:

- `system` добавляется первым сообщением, только если `system_prompt` задан.
- Ключи `temperature` / `max_tokens` добавляются **только** при `Some(_)`.
- Блок рассуждений пишется в формате провайдера (см. 6.1.1) и только если
  модель их поддерживает и хотя бы одно из полей задано.
- `stream` в MVP не пишется вовсе.

#### 6.1.1 Нормализация параметров под провайдера

Единственное место, где параметры «переводятся» в диалект провайдера:

```gleam
/// Приводит options к виду, который понимает конкретный провайдер,
/// и отсекает то, что модель не поддерживает.
pub fn normalize_options(
  provider: Provider,
  model: ModelInfo,
  options: RequestOptions,
) -> RequestOptions
```

Правила:

- У модели с `NoReasoning` (`haiku-4.5`, `gemini-3.5-flash-lite`) поля
  рассуждений обнуляются — иначе провайдер вернёт 400.
- `reasoning_effort` проверяется по `ReasoningSupport.efforts` выбранной
  модели. veai знает `xhigh`, kimi — нет: при смене провайдера значение вне
  шкалы заменяется ближайшим допустимым, а не отбрасывается молча.
- `AlwaysReasoning` (все модели kimi) игнорирует `reasoning_enabled` —
  выключить рассуждения нельзя, в UI тумблер неактивен.
- `temperature` зажимается в `0.0…2.0`, `max_tokens` — в
  `1…model.max_output_tokens` (если известен).

Нормализация вызывается **до** `build_request_body` и её результат
сохраняется в `messages.params_json` — то есть в БД лежит то, что
действительно ушло, а не то, что хотел пользователь.


Текущая реализация: `choices[0].message.content`, при не-2xx — разбор

### 6.3 `server/llm/client.gleam`

```gleam
/// ★ ТОЧКА РАСШИРЕНИЯ №3 (транспорт)
```

### 7.2 Sidebar (левая часть)

- Кнопка **«+ Новый чат»** — создаёт сессию и делает её активной.
- Список сессий: заголовок + время последнего изменения, новые сверху.
- Активная сессия подсвечена.
- По наведению — иконки «переименовать» (inline-input) и «удалить»
  (с подтверждением).

### 7.3 Dialog (правая часть)

- Поток сообщений, user справа / assistant слева (или цветовая разметка).
- Шапка сообщения: роль, модель (для ответа), время, длительность, компактная
  строка параметров (`t=0.7 · 4096 · effort=medium`), кнопка **`{} JSON ▸`**.
- Клик по `{} JSON` разворачивает блок `<pre>` с **форматированным**
  (pretty-printed, отступ 2) сырым JSON-ом и кнопкой «копировать».
  Состояние «развёрнуто» хранится в модели клиента как `Set(String)` id
  сообщений — переживает перерисовку, но не перезагрузку.
- Сообщение со `status = "error"` рисуется красным, в теле — текст ошибки,
  сырой ответ всё равно доступен в разворачивающемся блоке.
- **Вызов инструмента рисуется именем и аргументами**, а не пустым
  пузырём: у такого шага модели нечего сказать, вся суть в том, что она
  запросила. Результат приходит отдельной строкой с ролью «Инструмент».
- **Лента сессии агента двухуровневая.** Задание — карточка `.task`:
  шапка со статусом, текст задания, свёрнутые шаги, итог. Шаги внутри —
  те же самые пузыри `.message`, поэтому `{} JSON` и рассуждения работают
  там без доработок. У шагов нет кнопки `×`: удаляется задание целиком.
  Сессия без агента рисуется плоско, как раньше.
- **Удаление обмена.** Кнопка `×` в шапке, появляется при наведении на
  сообщение. Удаляет пару целиком (запрос + ответ): вопрос без ответа или
  ответ без вопроса в диалоге бесполезны. Кнопка есть у обоих сообщений
  пары — неважно, за какое потянули.
- Текст сообщений и раскрытый JSON показываются **целиком**: пузырь не
  сжимается flex-колонкой (`flex-shrink: 0`), у блока JSON нет жёсткого
  лимита высоты — только `max-height: 70vh` с собственной прокруткой для
  совсем больших тел.
- Пока ответ не получен — плейсхолдер «…» с индикатором загрузки.
- Автоскролл вниз при добавлении сообщения.

### 7.4 Composer (поле ввода)

- `textarea`, автоподстройка высоты. `Enter` — отправить,
  `Shift+Enter` — перенос строки.
- **Два `select` рядом с полем ввода**: провайдер и модель. Смена провайдера
  перезаполняет список моделей и выбирает первую. Выбор сохраняется в сессии
  (`sessions.provider_id` / `model_id`) и восстанавливается при её открытии.
- Недоступные провайдеры (нет ключа в env) — `disabled` с подсказкой.
- Модели в списке сгруппированы через `<optgroup>` по вендору; у провайдера
  с единственной группой заголовок не выводится.
- Кнопка **`⚙`** раскрывает панель параметров (см. 7.6).
- Кнопка **«Править JSON»** раскрывает редактор:
  - при раскрытии клиент запрашивает `POST /preview` и показывает
    сформированный сервером JSON в `textarea` моноширинным шрифтом;
  - JSON валидируется на лету, при ошибке кнопка «Отправить» блокируется и
    показывается сообщение парсера;
  - кнопка «Сбросить» перегенерирует JSON из текущего текста/модели;
  - если редактор открыт и JSON изменён — при отправке уходит
    `raw_request_override`.
- Во время запроса поле и кнопка блокируются.

### 7.6 Панель параметров

Ключевой принцип: **у каждого параметра есть чекбокс «использовать»**. Снятый
чекбокс = `None` = ключ не уходит в запрос вообще, решает провайдер. Это
прямое отображение `Option(..)` из `RequestOptions` в UI и единственный
честный способ отличить «температура 0» от «температуру не трогали».

| Параметр | Контрол | Диапазон / значения |
|---|---|---|
| `temperature` | слайдер + числовое поле | `0.0 … 2.0`, шаг `0.05` |
| `max_tokens` | числовое поле | `1 … model.max_output_tokens`, справа подпись с максимумом |
| `reasoning_enabled` | радио вкл/выкл | неактивно при `AlwaysReasoning` и скрыто при `NoReasoning` |
| `reasoning_effort` | сегментированные кнопки | строго из `ReasoningSupport.efforts` текущей модели |
| `system_prompt` | `textarea` | свободный текст |

Поведение:

- **Реакция на смену модели.** Панель перерисовывается под возможности новой
  модели: исчезают нерелевантные контролы, `max_tokens` переограничивается,
  шкала `effort` меняется (`xhigh` у veai есть, у kimi нет). Если текущее
  значение вне новой шкалы — оно заменяется ближайшим, и рядом один раз
  показывается ненавязчивая плашка с тем, что изменилось (те самые `warnings`
  из `/preview`).
- **Счётчик на кнопке `⚙`** показывает число активных (отмеченных)
  параметров — видно, что запрос не «чистый», не раскрывая панель.
- **«Сбросить всё»** возвращает все чекбоксы в снятое состояние
  (`default_options()`).
- **Параметры живут в сессии**: изменение шлёт `PATCH /api/sessions/:id` с
  `params` (с дебаунсом ~400 мс), при открытии сессии восстанавливаются.
  Разные сессии могут иметь разные настройки — удобно держать рядом
  «холодную» и «творческую».
- **Связь с редактором JSON.** Панель и ручной JSON — два вида на одно и то
  же. Правка параметра при открытом редакторе перегенерирует JSON через
  `/preview` (если пользователь его ещё не трогал руками). Если JSON уже
  правили вручную — панель переходит в режим «только для чтения» с пометкой
  «JSON отредактирован вручную, параметры не применяются» и кнопкой
  «вернуться к параметрам».
- Параметры каждого отправленного сообщения видны в его шапке компактной
  строкой (`t=0.7 · 4096 · effort=medium`) — чтобы при сравнении ответов не
  лезть в сырой JSON.

## 9. Нефункциональные требования

- Запрос к LLM не блокирует обслуживание других HTTP-запросов (wisp/mist
  обрабатывает каждый запрос в отдельном процессе — требование выполняется
  по умолчанию).
- Ошибка провайдера, таймаут и невалидный JSON **никогда** не роняют сервер:
  всё превращается в строку `assistant` со `status='error'`.
- Все записи сырых JSON-ов обязательны — без них теряется ключевая
  отладочная ценность каркаса.
- Некорректные параметры не должны приводить к 400 от провайдера:
  `normalize_options` обязана отсечь или подправить всё, что модель не
  поддерживает, **до** отправки.
- Логирование: метод, путь, статус, длительность; для LLM-запросов — провайдер,
  модель, http-статус, latency.

## 10. Вне рамок этапа

Намеренно **не** делаем сейчас, но архитектура не должна мешать добавить:

- передачу истории диалога в запрос (готово: `RequestContext.history`);
- стриминг ответа (готово: `RequestOptions.stream` + замена `client.send`);
- tools / function calling (в каталоге уже есть флаг `tools` у моделей);
- вложения и изображения (в каталоге есть флаг `vision`);
- пресеты параметров («точный» / «творческий») поверх панели ⚙;
- авторизацию, многопользовательский режим;
- поиск по сессиям, экспорт, markdown-рендер ответов;
- подсчёт стоимости по токенам (поле `usage` уже разбирается).

## 11. Дополнительные предложения

1. **Кнопка «повторить»** у ответа — переотправляет сохранённый
   `raw_request` той же или другой моделью. Стоит почти ничего (весь JSON
   уже в БД), а для сравнения моделей бесценно. Вариант «повторить с
   текущими параметрами» использует `messages.params_json` как основу.
2. **Метка «отредактировано вручную»** на сообщениях, отправленных с
   `raw_request_override` — чтобы при отладке было видно, что ушло не то,
   что сгенерировал код.
3. **Горячая клавиша `Ctrl+J`** — развернуть/свернуть JSON у последнего
   сообщения.
4. **Seed-сессия «Проверка связи»** при первом запуске с пустой БД — сразу
   есть куда нажать.
5. **`/api/health`** — отдаёт статус БД и наличие ключей; удобно в разработке.

## 13. Отклонения реализации от ТЗ

Решения, принятые по ходу работы. Описаны здесь, чтобы ТЗ оставалось
достоверным описанием того, что получилось.

### 13.1 Дополнения

- **Модуль `server/llm/chat.gleam`** — оркестрация поверх трёх точек
  расширения: связывает `prepare → send → parse` и пишет результат в БД.
  Сами точки расширения о нём не знают, поэтому менять их можно
  независимо. В ТЗ этот слой не был выделен явно.
- **Поле `Message.reasoning`** — рассуждения сохраняются отдельно от
  `content` и показываются сворачиваемым блоком. Без этого ответы kimi
  теряли бы половину содержимого.
- **`ReasoningSupport`** вместо плоских флагов: три варианта
  (`NoReasoning` / `OptionalReasoning` / `AlwaysReasoning`) оказались
  необходимы, потому что «модель не рассуждает» и «модель рассуждает
  всегда» требуют разного поведения UI.
- **Поля каталога `vision`, `tools`, `max_output_tokens`** — провайдеры их
  отдают, и они понадобятся для вложений и function calling.
- **`GET /api/sessions/:id`** — отдельный эндпоинт для одной сессии:
  клиенту нужно восстановить выбор модели и параметры при её открытии.
- **`DELETE /api/sessions/:id/messages/:mid`** — удаление обмена.
  Удаляет пару запрос+ответ и возвращает id удалённых строк, чтобы клиент
  убрал их из диалога без полной перезагрузки списка.
- **`GET /api/health`** — статус БД и наличие ключей (пункт 11.5 ТЗ).
- **Каталог Lustre `client/static/`** — свой `index.html`, потому что
  `lustre/dev build` генерирует собственный и называет бандл `client.js`.
- **`GET /api/sessions/:id/events`** — поток событий сессии по SSE
  (SPEC_AGENTS.md, п. 14). Единственный маршрут, который обрабатывается
  до wisp: `mist.server_sent_events` требует `Request(mist.Connection)`,
  а wisp этот тип уже спрятал. Весь остальной API живёт в `router.gleam`
  без изменений.

### 13.2 Изменения

- **Идентификаторы** — не UUID v4, а префикс + 22 символа base64url
  (`ses_a1b2…`). Та же энтропия, короче, и префикс помогает при чтении
  логов и содержимого БД.
- **`MessageStatus.Done`** вместо `Ok` — конструктор `Ok` перекрывал бы
  `Ok` из `Result`.
- **Ближайшее усилие при равном расстоянии** выбирается в большую сторону
  (`xhigh → max`, `medium → high` у kimi): лучше подумать дольше, чем
  молча срезать качество ответа.
- **Каталог двухуровневый** (`Provider → ModelGroup → ModelInfo`) — у veai
  36 моделей, плоский список неудобен.
- **Ручной JSON не переформатируется** — сохраняется ровно то, что ввёл
  пользователь. Он мог оформить тело по-своему, и подменять его невежливо.
- **Порядок сессий** дополнен `rowid DESC`: две сессии, созданные в одну
  миллисекунду, иначе выстраивались в произвольном порядке.

### 13.3 Найденное при проверке

- **`<select>` и атрибут `selected`.** Исходно выбранный пункт помечался
  атрибутом `selected` у `<option>`. В ряде реализаций DOM это
  рассинхронизируется с фактическим выбором, и сохранённая модель не
  восстанавливалась. Исправлено: `value` задаётся на самом `<select>`.
- **Сообщения об ошибках JSON различаются между движками.** V8, JSC и
  SpiderMonkey формулируют их по-разному; переводятся все три формата.
- **Гонка за `seq` при параллельной отправке.** `next_seq` читал
  `MAX(seq)` отдельным запросом, а вставка происходила уже после ответа
  провайдера — через секунды. Шесть одновременных `send` в одну сессию
  давали пять сообщений с одинаковым `seq`. В UI не проявлялось: клиент
  блокирует кнопку на время запроса.
  **Исправлено** (миграция 2): номер присваивается внутри
  `INSERT … SELECT … RETURNING seq`, уникальный индекс
  `(session_id, seq)` страхует от повторения.
- **Пара запрос-ответ определялась соседством `seq`.** Следствие
  предыдущего пункта: после атомарной вставки номера пары перестали быть
  соседними — между ними вклиниваются чужие параллельные запросы. Удаление
  обмена при этом оставляло ответ сиротой.
  **Исправлено**: связь хранится явно в `messages.reply_to`. У строк,
  записанных до миграции 2, поле `NULL`, и для них работает прежний поиск
  по соседству — старые диалоги продолжают удаляться парами.
- **Пузыри сообщений обрезали текст.** В flex-колонке элементы по
  умолчанию сжимаются (`flex-shrink: 1`), а `overflow: hidden` на
  `.message` превращал это в видимую обрезку: у длинных ответов
  показывалась только первая строка. Лечится `flex-shrink: 0`.
  Заодно снят `max-height: 420px` у раскрытого JSON — он прятал концовку
  как раз тех ответов, ради которых блок и раскрывают.
- **`prevent_default` на `keydown`** нельзя вешать безусловно — это
  сломало бы ввод текста. Используется `event.advanced`, отменяющий
  поведение только для Enter без Shift.
- **Песочница `read_file` обходилась через `..`.** Первая версия
  канонизации пути (`server_path_ffi.erl`) разворачивала символические
  ссылки, но не схлопывала `..`, и проверка «начинается с корня»
  проходила обманом: `root/../../etc/passwd` формально начинается с
  `root`. Поймано тестом на обход.
  **Исправлено**: путь обходится посегментно сверху вниз, ссылки
  разворачиваются по ходу, `..` схлопывается после них. Порядок важен —
  иначе `link/..` вёл бы туда, где лежит ссылка, а не туда, куда она
  показывает.
- **Сравнение с корнем по префиксу строки** пускало соседа с похожим
  именем: `/tmp/box-secret` «начинается с» `/tmp/box`. Сравнение идёт с
  разделителем.
- **`rand:uniform(N)` возвращает 1…N**, а не 0…N−1, как в большинстве
  языков. Прибавление единицы давало семёрку на шестигранном кубике.
- **Пустые `user`-сообщения уходили провайдеру.** У шага, инициированного
  циклом агента, текст запроса пуст: строка существует ради
  `raw_request`. В теле запроса это давало пустое `user` между
  результатом инструмента и следующим ответом. Исправлено фильтром по
  содержимому.
- **Фильтр по статусу сломал делегирование.** Убирая пустые строки, я
  заодно отбросил сообщения со `status = error` — а неудачный вызов
  инструмента помечен именно так. Модель переставала видеть отказ,
  просила то же самое снова и упиралась в лимит шагов. Отказ — это
  ответ, а не отсутствие ответа.
- **`attr("checked", "")` отмечает чекбокс.** Пустое значение атрибута не
  делает его отсутствующим, поэтому все инструменты в форме агента
  выглядели выбранными. Нужен `attribute.checked(Bool)`. Поймано
  скриншотом, а не DOM-тестом: тест смотрел на состояние модели, где всё
  было верно.
- **Поток событий не открывался при автовыборе сессии.** Подписка стояла
  на явном выборе в списке, а первая сессия открывается при загрузке
  сама, минуя этот путь. Живое обновление работало везде, кроме самого
  частого случая. В ручной проверке незаметно: достаточно один раз
  кликнуть по соседней сессии, и всё начинает работать.
