# LLM-чат на Gleam

Каркас веб-приложения для общения с языковыми моделями через API
нескольких провайдеров. Подробное техническое задание — в [SPEC.md](SPEC.md).

Переделка домена под агентов (агент → сессия → задание → шаг) описана
отдельно в [SPEC_AGENTS.md](SPEC_AGENTS.md).

## Быстрый старт

```bash
export OPENAI_API_KEY=...   # ключ VeAI
export KIMI_API_KEY=...     # ключ Kimi

./run.sh                    # собрать клиент и поднять сервер
```

Интерфейс — <http://localhost:8080>.

Без ключей приложение тоже запустится: интерфейс и предпросмотр запроса
работают, но отправка будет заблокирована, а провайдер помечен «нет ключа».

## Команды

| Команда | Что делает |
|---|---|
| `./run.sh` | Собрать клиент и запустить сервер |
| `./run.sh build` | Только собрать клиент |
| `./run.sh serve` | Только запустить сервер |
| `./run.sh test` | Юнит-тесты пакетов `shared` и `server` |
| `./run.sh e2e` | UI-тесты в браузерном окружении |
| `./run.sh check` | Сборка + все тесты |
| `./run.sh catalog` | Обновить каталог моделей из API провайдеров |

## Структура

```
shared/   типы, JSON-кодеки, каталог моделей  (erlang + javascript)
server/   HTTP API, SQLite, вызовы провайдеров (erlang)
client/   Lustre SPA                          (javascript)
e2e/      UI-тесты поверх собранного клиента
scripts/  генератор каталога из ответов /models
```

## Точки расширения

Главная задача каркаса — изолировать то, что будет меняться. Три функции
с замороженными сигнатурами:

| Файл | Функция | Отвечает за |
|---|---|---|
| `server/src/server/llm/request.gleam` | `build_request_body` | сборку тела запроса |
| `server/src/server/llm/response.gleam` | `parse_response_body` | разбор ответа |
| `server/src/server/llm/client.gleam` | `send` | транспорт |

Плюс `normalize_options` в `request.gleam` — приведение параметров к
возможностям конкретной модели.

Разделение позволяет менять формат запроса, формат ответа и транспорт
независимо. Например, переход на стриминг затрагивает только `client.send`.

Задел на будущее, уже присутствующий в типах:

- `RequestContext.history` — история диалога (сейчас всегда `[]`);
- `RequestOptions.stream` — стриминг;
- флаги `vision` и `tools` у моделей — вложения и function calling;
- `ParsedResponse.usage` — подсчёт стоимости.

## Как это работает

### Независимость запросов

На этом этапе каждый запрос самостоятелен: история диалога модели не
передаётся. Поле `history` в `RequestContext` уже есть, и включение
мультитёрнового режима сведётся к тому, чтобы начать его заполнять.

### Параметры запроса

У каждого параметра в панели `⚙` есть чекбокс «использовать». Снятый
чекбокс означает, что ключ **не уходит в запрос вообще** — решает
провайдер. Это прямое отображение `Option(..)` в интерфейс и единственный
способ отличить «temperature = 0» от «температуру не трогали».

Параметры хранятся на двух уровнях:

- `sessions.params_json` — текущая настройка сессии, восстанавливается
  при её открытии;
- `messages.params_json` — неизменяемый снимок на момент отправки, чтобы
  потом понять, с какими параметрами получен конкретный ответ.

### Различия провайдеров

Главное расхождение — рассуждения:

| | VeAI | Kimi |
|---|---|---|
| Шкала усилий | `low` `medium` `high` `xhigh` `max` | `low` `high` `max` |
| Можно выключить | да | нет, рассуждает всегда |
| Лимит вывода | сообщает | не сообщает |
| Моделей без reasoning | 2 | 0 |

`normalize_options` сглаживает эти различия до отправки: значение вне
шкалы заменяется ближайшим (при равном расстоянии — большим), несовместимые
поля отбрасываются, а пользователь видит список поправок.

### Сырые JSON

Тело каждого запроса и ответа сохраняется в БД как есть и разворачивается
в интерфейсе кнопкой `{} JSON`. Форматирование делает клиент, поэтому база
не распухает отступами. Ошибки провайдера тоже сохраняют сырое тело — в
этом основная отладочная ценность каркаса.

Кнопка `×` в шапке сообщения (появляется при наведении) удаляет обмен
целиком — и вопрос, и ответ: поодиночке они бесполезны.

Ключ API никогда не попадает в `raw_request`: он живёт только в заголовке
`Authorization`, который не сохраняется.

### Ручная правка JSON

Кнопка «Править JSON» показывает тело, собранное сервером. Если его
изменить, оно уйдёт провайдеру **как есть** — сервер лишь проверит, что это
разбираемый JSON-объект. Панель параметров при этом переходит в режим
только для чтения, потому что применять параметры поверх ручного тела было
бы неожиданно.

### Агенты

Кнопка **«Агенты»** в боковой панели открывает экран настройки: список,
форма создания и правки, запуск. Агент — настроенный исполнитель: имя,
системный промпт, модель, предел шагов и список инструментов задаются один
раз и переиспользуются.

**«Запустить»** создаёт сессию этого агента. В ней ввод выдаёт не
сообщения, а задания: одно задание — одна карточка в ленте, внутри неё
свёрнут обмен с моделью. Обычный чат («+ Новый чат») работает как раньше.

Удалить агента, у которого есть запуски, нельзя — сессии осиротели бы.
Сначала удаляются они.

### Память агента

По умолчанию каждое задание начиналось с чистого листа. Теперь агент
помнит разговор — настраивается в форме, четырьмя независимыми
переключателями:

- **Из прошлых заданий:** ничего / задание и итог / весь обмен / всю
  историю. «Задание и итог» дёшево по контексту и обычно достаточно,
  чтобы не терять нить.
- **Сжимать вытесненное** каждые N сообщений: модель пересказывает то,
  что вышло за окно. Пересказ не удаляет сообщения — исходные шаги
  остаются в базе со всеми сырыми телами.
- **Подставлять факты:** инструменты `remember` и `forget`. Агент сам
  решает, что важно запомнить на весь запуск. Факты не вытесняются.
- **Предел истории** в символах. Последний рубеж: любая комбинация
  рано или поздно переполнит контекст, и лучше срезать старое самим,
  чем получить отказ провайдера. 0 — четверть контекста модели.

Строка над лентой показывает расход токенов за сессию и раскрывается в
панель: запрос, ответ, запомненные факты, текущий пересказ.

### Наблюдение в реальном времени

Задание из нескольких шагов выполняется долго, и ждать его молча незачем:
шаги появляются в ленте по мере готовности. Поток идёт по SSE —
`GET /api/sessions/:id/events`, подписка на сессию, а не на задание,
поэтому переподключаться при выдаче нового задания не нужно.

По потоку передаются **готовые шаги, а не токены**. Побуквенный набор
ответа разрушил бы свойство, на котором держится весь каркас: «в БД лежит
ровно то, что ушло и пришло». Частичный ответ нечем проверить и не с чем
сравнить. Выгода при этом несимметрична: шаги превращают минуту тишины в
видимую работу, токены лишь украшают последние секунды.

Поток **дополняет** обычные запросы, а не заменяет их. При открытии сессии
данные по-прежнему грузятся запросом, задание отправляется блокирующим
`POST`, а SSE даёт изменения по дороге. Поэтому обрыв связи ничего не
ломает: результат придёт с ответом, как и раньше.

### Инструменты агента

Агент может вызывать инструменты: `now`, `calc`, `roll_dice`, `find_task`,
`read_file`, `http_request`, `call_agent`. Список вкомпилирован в
приложение, доступ каждому агенту выдаётся **явно** — по умолчанию у него
нет ничего.

Каждый вызов — обычный шаг в ленте со своими сырыми JSON: видно, что
модель просила и что получила в ответ. Ошибка инструмента возвращается
модели как результат, чтобы та могла исправиться, и помечается в БД
`status = error`; задание при этом продолжается.

Опасные инструменты ограничены (см. переменные окружения ниже):

- `read_file` читает только внутри `AGENT_FILES_ROOT`. Путь приводится к
  каноническому виду — с развёрнутыми `..` и символическими ссылками —
  и только потом проверяется на принадлежность корню. Проверять до
  развёртывания бессмысленно: обойти можно и тем, и другим.
- `http_request` ходит только к хостам из `AGENT_HTTP_ALLOWLIST`. Адреса
  внутренней сети запрещены даже при попадании в список — иначе агент
  дотянулся бы до собственного API сервера.
- `call_agent` защищён тремя способами сразу: предел глубины, запрет
  повторного появления агента в цепочке вызовов и общий бюджет шагов на
  всё дерево. Вложенный запуск создаёт свою сессию («Второй ← Первый»),
  поэтому работа подагента видна обычным образом.

## Каталог моделей

Список моделей вкомпилирован в приложение
(`shared/src/shared/catalog/generated.gleam`) — на рантайме запросов за ним
нет. Файл генерируется из ответов `/models`:

```bash
./run.sh catalog     # обновить из API и перегенерировать
```

Сырые ответы (`modeles.txt`, `kimi_models.txt`) лежат в репозитории как
справочник по возможностям моделей.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `OPENAI_API_KEY` | — | Ключ VeAI |
| `KIMI_API_KEY` | — | Ключ Kimi |
| `VEAI_BASE_URL` | `https://api.veai.ru/openai/api/v1` | |
| `KIMI_BASE_URL` | `https://api.kimi.ai/coding/v1` | |
| `PORT` | `8080` | Порт сервера |
| `DB_PATH` | `data/chat.db` | Файл SQLite |
| `REQUEST_TIMEOUT_MS` | `120000` | Таймаут запроса к провайдеру |

Ограничения инструментов агента. Всё опасное выключено по умолчанию:
доступ к файлам и сети — осознанное решение, а не следствие
невнимательности.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `AGENT_FILES_ROOT` | — | Корень песочницы для `read_file`. Не задан — инструмент недоступен |
| `AGENT_MAX_FILE_BYTES` | `64000` | Предел размера читаемого файла |
| `AGENT_HTTP_ALLOWLIST` | — | Хосты для `http_request` через запятую. Пусто — сеть запрещена |
| `AGENT_MAX_HTTP_BYTES` | `64000` | Предел размера ответа, сверх него тело обрезается |
| `AGENT_MAX_DEPTH` | `3` | Предел вложенности `call_agent` |

## Тесты

```bash
./run.sh check
```

- **171 юнит-тест** — кодеки, каталог, сборка запроса, нормализация
  параметров, разбор ответов, репозитории, цикл агента, инструменты,
  границы песочницы, шина событий, слои памяти и бюджет.
- **75 контрактных проверок** (`e2e/api_contract_test.mjs`) — форма всех
  HTTP-эндпоинтов без участия интерфейса.
- **48 проверок API агентов** (`e2e/agents_contract_test.mjs`) — агенты,
  запуски и задания.
- **15 проверок параллельной работы** (`e2e/09_concurrency_test.mjs`) —
  одновременные отправки не путают нумерацию и не теряют пары.
- **29 проверок песочницы** (`e2e/12_sandbox_test.mjs`) — выход за корень,
  чужой хост, рекурсия и предел глубины делегирования против живого цикла.
- **27 проверок потока событий** (`e2e/13_events_test.mjs`,
  `14_live_updates_test.mjs`) — шаг виден до завершения задания, события
  не утекают между сессиями, обрыв подписки не ломает агента.
- **27 проверок экрана агентов** (`e2e/15_agents_ui_test.mjs`) — путь
  целиком: пустой список → форма → запуск → задание через инструмент.
- **28 проверок памяти** (`e2e/16_memory_test.mjs`) — прошлое доходит до
  модели, окно ограничено, бюджет срезает лишнее, сессии изолированы.
- **279 UI-проверок** — интерфейс исполняется в DOM-окружении против
  живого сервера; вместо провайдера отвечает мок, поэтому токены не
  расходуются.

Контрактный тест стоит отдельно от UI-тестов намеренно: он описывает
границу между клиентом и сервером. При переделке бэкенда это точка опоры —
пока он зелёный, интерфейс продолжит работать.

```bash
./e2e/run.sh api_contract    # только контракт, ~5 секунд
```

UI-тесты стартуют с чистой БД каждый: сервер запоминает выбор модели в
сессии, и состояние от предыдущего теста повлияло бы на следующий.

- Gleam 1.19+, Erlang/OTP
- `jq` — для генерации каталога
- Bun скачивается автоматически через `lustre_dev_tools`; Node.js не нужен
